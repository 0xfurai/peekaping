## [Unreleased]

### Added

- feat: the first step to workspaces ([ADR 0005](docs/adr/0005-workspaces-and-data-isolation.md)). An install that upgrades gets one workspace, "My workspace", and its users become its owners and instance admins. On a new install the first user to sign up gets it. Nothing changes in the app yet. `bun db import-mongo` gives the database it fills the same workspace
- feat: a request runs in a workspace ([ADR 0005](docs/adr/0005-workspaces-and-data-isolation.md)). A signed-in request names its workspace with an `X-Workspace-ID` header and runs in the user's first workspace without it; a workspace the user isn't in answers 404. An API key belongs to the workspace it was created in and runs there as an admin. `GET /api/v1/me` returns the signed-in user, their workspaces with their role in each, and the default one. Upgraded installs' API keys move to their one workspace and keep working. A self-hoster sees no change.
- feat: only an admin or owner of a workspace manages its API keys, and only an instance admin turns the usage ping and error reports on or off. The first user, and every user of an upgraded install, is one.
- feat: monitors belong to a workspace ([ADR 0005](docs/adr/0005-workspaces-and-data-isolation.md)). A monitor made through the API belongs to the workspace of the request, and its heartbeats, stats and TLS info go with it; another workspace's member gets 404 for it on every route. An upgraded install's monitors move to its one workspace, and `bun db import-mongo` puts imported monitors in the workspace it makes. Checks, pushes, probes, notifications, public status pages, badges and `/metrics` keep working across workspaces. A self-hoster sees no change.
- feat: account emails. Set `ACCOUNT_SMTP_HOST` (with `ACCOUNT_SMTP_FROM`, and `ACCOUNT_SMTP_PORT`, `ACCOUNT_SMTP_USER`, `ACCOUNT_SMTP_PASSWORD` and `ACCOUNT_SMTP_TLS` as needed) and the install sends the emails of an account from one sender. `POST /api/v1/auth/forgot-password` emails a single-use link that expires in an hour and answers the same for every address; `POST /api/v1/auth/reset-password` sets the new password with it and ends every session of the user, access tokens and refresh tokens alike. Every new account (the first user, a signup through an invite, later open signup) gets a verification link that expires in three days (`POST /api/v1/auth/verify-email`), a signed-in user can ask for it again (`POST /api/v1/auth/verify-email/resend`), and `GET /api/v1/me` returns `user.emailVerified` and `accountEmails`. An invite is also emailed to the invitee, and the copyable link stays. Asking for a reset or verification link is limited to 5 emails an hour per address and 20 requests per client address. `GET /api/v1/auth/config` is public and says whether account emails are on. With `ACCOUNT_SMTP_HOST` unset, which is the default, nothing changes: no reset link, no verification and invites are copied. See [Account Emails Configuration](apps/docs/docs/architecture/api-server.md#account-emails-configuration)
  - Upgrade note: the upgrade adds `users.email_verified_at` and `users.tokens_valid_after` and an `account_tokens` table, and counts every existing user as verified. Access tokens now carry their issue time to the millisecond.
- feat: signup modes. `SIGNUP_MODE` is `invite` (the default, and what an install that sets nothing gets: the first user signs up and everyone after joins through an invite) or `open`, where anyone may sign up and gets a workspace of their own, as its owner. Only the install's first user is an instance admin, and someone who signs up through an invite joins the inviting workspace instead. Any other value stops startup, and so does `open` without a sender for account emails (`ACCOUNT_SMTP_HOST`), since each new account must verify its email address. In `open` mode the workspace of a new account is suspended until its owner verifies their email address (or resets the password with the emailed link): its monitors can be created and are listed, but none runs, no check, missed-push detection or notification, and a push to its URL answers 403. `GET /api/v1/me` marks such a workspace with `suspended` and `suspendedReason`. In `open` mode a signup with an email that has an account answers 409, which tells the visitor that the address is registered. Open signups are limited to 5 an hour per client address, and `SIGNUP_TURNSTILE_SITE_KEY` with `SIGNUP_TURNSTILE_SECRET` makes `POST /api/v1/auth/register` need a Cloudflare Turnstile `turnstileToken` that the server checks. `GET /api/v1/auth/config` returns `signupMode`, `signupOpen` and `turnstileSiteKey`. See [Signup Configuration](apps/docs/docs/architecture/api-server.md#signup-configuration)
  - Upgrade note: the upgrade adds `workspaces.suspended_at` and `workspaces.suspended_reason`. Nothing existing is suspended, and an install that sets nothing behaves as before.
- feat: an admin or owner of a workspace renames it with `PATCH /api/v1/workspace` and a body `{"name": "..."}` (1 to 255 characters, trimmed). It answers 200 with the workspace as `POST /api/v1/workspaces` does, a member gets 403, and a workspace the caller isn't in answers 404. An API key renames the workspace it belongs to, as an admin.
- feat: the install email notification channel (type `install_email`, config `{"to": "..."}`) sends a notification through the install's sender for account emails (`ACCOUNT_SMTP_HOST`) to one address, which must be the email of a member of the channel's workspace. Creating, updating or testing one with another address answers 400, and so does creating, updating or testing one on an install without a sender. The address is checked again at each send: a recipient who has left the workspace gets nothing, and the failed send is logged. A send, a test included, also needs that member to have verified their email address; saving the channel does not. A test to an unverified member answers 400, and nothing is sent. The SMTP channel, with its own server and any recipient, is unchanged.

- feat: `DISABLED_MONITOR_TYPES` is a comma-separated list of monitor types that an install turns off, empty by default (the cloud sets `docker`, since the Docker monitor reads the Docker socket of the machine the server runs on). A type the server doesn't know stops startup and lists the known ones. Creating a monitor of a disabled type, or changing a monitor's type to one, answers 400 with the code `MONITOR_TYPE_DISABLED`. A monitor that already has such a type is kept and returned with `type_disabled: true`, but is not checked, not by the scheduler, a remote probe or a push (which answers 403), and nothing notifies for it; its stored `active` and probes are left alone, so it runs again once the variable is unset. A public status page lists it with `active: false`. `GET /api/v1/me` returns `disabledMonitorTypes`. See [Monitor Types Configuration](apps/docs/docs/architecture/api-server.md#monitor-types-configuration)
- feat: `BLOCK_PRIVATE_TARGETS` keeps monitors from reaching the internal network. It is off by default, so a self-hosted install is unchanged (the cloud turns it on). With it on, every monitor type that connects out is covered: the HTTP (including the OAuth token request, mTLS, NTLM and HTTP and SOCKS proxies), TCP, ping, DNS, SMTP, SNMP, PostgreSQL, MySQL, SQL Server, MongoDB, Redis, MQTT, RabbitMQ, Kafka, gRPC and Docker checks can't reach loopback, the private ranges and `100.64.0.0/10`, `0.0.0.0/8`, link-local addresses (cloud metadata at `169.254.169.254` among them), IPv6 unique-local and link-local addresses, multicast and broadcast; an IPv4-mapped IPv6 address counts as its IPv4 address, and Unix sockets are blocked. The address a check connects to is checked, so a hostname that resolves to a blocked address, a redirect to one and a changing DNS answer are all refused, and the check is Down with "target address is not allowed". With it on, creating or updating (`PUT` or `PATCH`) a monitor whose target is a blocked IP address, or a proxy whose host is one, answers 400 with the code `TARGET_NOT_ALLOWED`; a hostname is saved and checked at each check. `peekaping-probe` reads the same variable, and also blocks when the server it connects to does: the server states it in the new `block_private_targets` field of the probe hello answer, which an older server leaves out (off). A probe says in its hello that it follows the server's setting (`enforces_private_target_block`), and a server with the setting on deals no monitors to an instance of an older probe, which would ignore it: it logs a warning once for each such instance, and the probe API lists it with `enforces_private_target_block: false`. Upgrade the probes before turning the setting on. The protocol version is unchanged. A Docker monitor over a Unix socket is refused with it on. See [Blocking private targets](apps/docs/docs/architecture/api-server.md#blocking-private-targets)
  - Upgrade note: the upgrade adds `probe_instances.enforces_private_target_block`. Every instance on record counts as one of an older probe until it says hello again, which a probe does when it loses the server, as it does while the server restarts.
- feat: `BLOCK_PRIVATE_TARGETS` covers notification channels too. With it on, the webhook, Slack, Discord, Teams, Google Chat, Mattermost, WeCom, ntfy, Gotify, Matrix, Signal, Telegram, WhatsApp, PagerDuty, PagerTree and Grafana OnCall channels and the SMTP channel's server can't reach the addresses a check can't: a URL that is a blocked address, a name that resolves to one and a redirect to one send nothing. Creating, updating or testing a channel whose URL or SMTP host is a blocked IP address answers 400 with the code `TARGET_NOT_ALLOWED`; a test that dials a name resolving to a blocked address answers 400 with "target address is not allowed". The account emails and the install email channel are not checked. A proxy from the server's environment (`HTTPS_PROXY`, `HTTP_PROXY`) is the install's own and is connected to wherever it is, and a request's target is checked before it goes to the proxy. With it off, nothing changes. See [Blocking private targets](apps/docs/docs/architecture/api-server.md#blocking-private-targets)
- feat: `API_RATE_LIMIT_PER_WORKSPACE` and `API_RATE_LIMIT_PER_API_KEY` limit the requests per minute a workspace, and one of its API keys, may make. Both are `0` (off) by default, so an install that sets nothing is unchanged. A request over either, signed in or by API key, answers 429 with `{"message": "Too many requests, try again later"}` and a `Retry-After` header in seconds; every request of an API key also counts toward its workspace's limit. Routes that run in no workspace (`/me`, `/auth/*`, `/admin/*`, creating a workspace, accepting an invite) are not counted. Each api replica keeps its own count, so an install with several replicas allows each replica's share. A negative value stops startup. The 429 of an invite, a password reset or verification email, and an open signup now send `Retry-After` too, and the API description lists the header on every 429 it documents. See [API rate limits](apps/docs/docs/architecture/api-server.md#api-rate-limits)
- feat: `CHECKS_PER_HOST_PER_MINUTE` caps how many checks to one target host run per minute in one checking process (the scheduler of `peekaping`, the api's push checks, or one `peekaping-probe` instance), across all monitors and workspaces. It is `0` (off) by default, so an install that sets nothing is unchanged; a negative value stops startup. Checks to a host are spaced evenly (60 a minute is one a second). A check whose turn is at most a quarter of its interval away, and at most 5 seconds, waits for it before its own timeout starts; a check further out skips that tick, with no heartbeat, no Down and no check slot held, and logs at debug level with the host and, at most once a minute per host, at info with the number skipped. The host is the one the check dials; push monitors and monitors under maintenance are never limited. A remote probe uses the stricter of its own `CHECKS_PER_HOST_PER_MINUTE` and the server's, which the server states in the new `checks_per_host_per_minute` field of the probe hello answer (an older server leaves it out, which means off, and an older probe ignores it, so the protocol version is unchanged). See [Spacing checks to one host](apps/docs/docs/architecture/api-server.md#spacing-checks-to-one-host)
- feat: `MIN_CHECK_INTERVAL` sets the smallest check interval and retry interval, in seconds, a monitor can be saved with. It is `20` by default, which is the smallest a monitor can have, so an install that sets nothing is unchanged; a value below 20 stops startup, since the timeout minimum (16) and the rule that a timeout is at most 0.8 times the interval rely on it. Creating a monitor or updating one (`PUT` or `PATCH`) with an `interval` or `retry_interval` below it answers 400 with the code `INTERVAL_TOO_SHORT`, the field and the minimum, and a message that names the minimum in seconds; a `PATCH` that sends neither is not refused because of a lower stored value. A monitor stored with less (saved before the minimum was raised, or imported) is checked at the minimum, by the scheduler, the stale-monitor watchdog and in the assignments a remote probe is dealt, while the API still shows what is stored; its timeout is kept as stored. `GET /me` returns the minimum as `minCheckInterval`, and the monitor form and Get started use it as their minimum and default interval. See [Minimum check interval](apps/docs/docs/architecture/api-server.md#minimum-check-interval)
- feat: workspace limits. A workspace's limits come from its own, which an instance admin sets ("no limits" is a value of its own), or else the install's defaults, the `WORKSPACE_LIMIT_*` variables, or else none: every variable is unset (`0`) by default, so an install that sets nothing has no limits. `WORKSPACE_LIMIT_MONITORS` caps the active monitors: creating an active monitor, or resuming one (`PATCH` or `PUT` with `active: true`), at the limit answers 403 with `{"error": {"code": "LIMIT_REACHED", "limit": "monitors", "max": 10}}`, and two such requests at once can't both take the last place. Lowering a limit pauses and deletes nothing: the oldest active monitors up to it run, the newer ones are kept but not checked, say `over_limit: true` and show as paused with the reason, and run again once the limit is raised or the owner pauses older ones. `WORKSPACE_LIMIT_MIN_CHECK_INTERVAL` applies beside `MIN_CHECK_INTERVAL`, on save and in the checks, and the stricter wins. `WORKSPACE_LIMIT_PROBES_PER_MONITOR` refuses more `probe_ids` (`LIMIT_REACHED`, limit `probes`), cuts the default probes of a new monitor to the first ones, and assigning a probe to every monitor skips the monitors at their limit. `WORKSPACE_LIMIT_STATUS_PAGES` refuses a status page create at the limit (limit `status_pages`), and `WORKSPACE_LIMIT_CUSTOM_DOMAINS` a create or update whose `domains` take the workspace's pages past it together (`custom_domains`). `WORKSPACE_LIMIT_MEMBERS` counts the members and the pending invites when an invite is made, and the members alone when one is accepted, signed in or through a signup, so a counted invite can still be used (`members`). `WORKSPACE_LIMIT_OWNED_WORKSPACES` refuses `POST /workspaces` to a user who owns as many, counted per user against the install's default alone (`owned_workspaces`). Each is safe against two writes at once. `GET /api/v1/workspace/limits` shows any member each limit with its value (`null` for none), its source (`workspace`, `install` or `none`) and the usage. An instance admin gives a workspace limits of its own with `PATCH /api/v1/admin/workspaces/{id}` and `{"limits": {...}}` (`{}` is no limits at all), removes them with `{"clearLimits": true}`, each logged, and the admin list shows every workspace's `limits`; `suspended` is no longer required there, but the request names at least one of the three. `WORKSPACE_LIMIT_RETENTION_DAYS` caps the data retention period: saving a longer `KEEP_DATA_PERIOD_DAYS` answers 403 `LIMIT_REACHED` (limit `retention_days`), one at the cap is saved, and the hourly cleanup deletes each workspace's heartbeats past the shorter of its own period and its cap, so lowering the cap trims the history on the next run; stats keep their install-wide retention. The workspace's Settings page shows the cap beside the field. See [Limits](apps/docs/docs/architecture/api-server.md#limits)
- feat: the install's default limits are install settings. An instance admin saves each under Admin → Settings, or with `PUT /api/v1/admin/settings` and `workspaceLimits` (`{"monitors": 10}` saves one, `null` clears it, a limit left out stays), unless its `WORKSPACE_LIMIT_*` variable is set, which wins and locks it (409 `SETTING_LOCKED`). A saved default is a whole number of 1 or more, `min_check_interval` at least `MIN_CHECK_INTERVAL` and `retention_days` at most 36500 (400 `INVALID_SETTING`), and it applies with no restart to every workspace without limits of its own, on the other api replicas within 5 seconds. `GET /api/v1/admin/settings` shows each with its value, source and lock. An install that sets nothing and saves nothing still has no limits
- feat: the web app words a write over a limit in the user's language, such as "This workspace can have at most 10 monitors running", when it creates, resumes or edits a monitor, creates or edits a status page, invites someone, accepts an invite or signs up through one, and creates a workspace. The monitor form, and Get started's first monitor, start at the shortest check interval that applies to the workspace. Admin → Workspaces shows each workspace's limits and where they come from, and sets its own, no limits, or the install's defaults again; Admin → Settings has the default limits, of every workspace without limits of its own
- feat: the admin area lists and suspends workspaces ([ADR 0005](docs/adr/0005-workspaces-and-data-isolation.md), section 10). `GET /api/v1/admin/workspaces?q=&page=&limit=` lists every workspace of the install with its name, when it was created, its owners' emails, how many members it has, how many monitors are active and paused, how many status pages and custom domains it has, and whether, why and since when it is suspended; `q` finds a name or an owner's email, ignoring case, and paging is that of `/admin/users`. It returns counts and metadata only, never a monitor's target, a channel or anything else inside a workspace. `PATCH /api/v1/admin/workspaces/{id}` with `{"suspended": true}` suspends a workspace and `false` resumes it: while suspended its monitors stop running (no checks, no missed-push detection, no notifications; a push answers 403) and `GET /api/v1/me` gives `suspendedReason` `admin`; nothing is deleted, and resuming brings it back as it was, with the monitors in the state they had. The admin's suspension is a hold of its own beside the one that waits for the owner's email verification, so resuming a workspace that still waits for verification leaves it waiting. Both are instance admin only (anyone else, and any API key, gets 403) and each suspend and resume is logged with who did it. Upgrade note: the upgrade adds `workspaces.admin_suspended_at`; nothing existing is suspended.
- feat: an instance admin deletes a workspace ([ADR 0005](docs/adr/0005-workspaces-and-data-isolation.md), section 10). `DELETE /api/v1/admin/workspaces/{id}` answers 204 and removes the workspace with everything in it: its monitors with their heartbeats and stats, notification channels, proxies, tags, maintenance windows, status pages and custom domains, API keys, invites and settings, by cascade, so no row is left behind. Its monitors stop at once, its public status pages and badges are gone, and its members' open sockets leave its rooms. Its members keep their accounts and their other workspaces; a member who had only this workspace gets `GET /api/v1/me` with an empty `workspaces` list. An unknown workspace is 404, anyone but an instance admin signed in as a user (and any API key) is 403, an admin may delete a workspace they are in, and the delete is logged with who did it.
- feat: install settings in the admin area ([ADR 0005](docs/adr/0005-workspaces-and-data-isolation.md), section 5). An instance admin changes the signup mode, the sender of account emails and the public URL without editing a compose file or restarting: `GET /api/v1/admin/settings` returns each with its value, where it comes from (`environment`, `saved` or `default`) and whether it is `locked`, and `PUT /api/v1/admin/settings` saves a partial change. Each value comes from the environment first, then the saved value, then the default, so a variable that is set (`SIGNUP_MODE`, `ACCOUNT_SMTP_*`, `CLIENT_URL`) wins and locks its setting: changing it answers 409 `SETTING_LOCKED`. Any `ACCOUNT_SMTP_*` variable that is set locks the whole sender. A value a setting can't hold is 400 `INVALID_SETTING` with the field; open signup without a sender is 400 `OPEN_SIGNUP_NEEDS_SENDER`, and removing the sender while signup is open is 400 `SENDER_NEEDED_FOR_OPEN_SIGNUP`. The SMTP password is never returned, only whether one is set, and a change that leaves it out keeps it, unless it changes the host, port, TLS mode or user: then the saved password is cleared and is entered again. `POST /api/v1/admin/settings/test-email` with `{"to": "..."}` sends a test email through the current sender (400 `NO_SENDER` without one, 502 with the SMTP reply code when it fails). A saved change takes effect at once, and on other api replicas within 5 seconds. Every change is logged with who made it and the settings it changed. An install that sets nothing and saves nothing behaves as before. See [Install settings](apps/docs/docs/architecture/api-server.md#install-settings)
- feat: Admin → Settings in the web app. An instance admin sets the signup mode (invite only or open), the email sender (host, port, TLS, user, password, from address) and the public URL there, and sees where each value comes from: the server's environment, saved here, or the default. A field the environment sets is read-only. The password field is never filled in: it says whether one is set, typing replaces it, and "Remove password" clears it. Save sends only the fields that changed, and a refusal says why, such as open signup without a sender. "Send a test email" checks the saved sender, sending to the admin's own address unless they type another. The usage statistics and error report switches moved here from a workspace's Settings page, and the upgrade notice links here
- feat: `SUPPORT_CONTACT` is how a member of a suspended workspace gets in touch with whoever runs the install: free text, an email address or a URL, empty by default. `GET /api/v1/me` returns it as `supportContact` (`null` when unset), for the suspension banner.

### Changed

- feat: push tokens and custom domains are unique across the install, and the database enforces both. A custom domain is stored lower-case and trimmed, and looked up the same way, so `Status.Example.com` is `status.example.com`. A monitor without a push token stores none, and a push or API write with a token another monitor holds is refused with a 400 and the code `PUSH_TOKEN_EXISTS`, as a domain another status page holds is refused with `DOMAIN_EXISTS`. Deleting a monitor now deletes its TLS information and its certificate notification history too
  - Upgrade note: the upgrade stops, before it changes anything, when two monitors share a push token or two status pages share a custom domain (ignoring case and spaces). The error names the monitors, or the domain and the status pages, and leaves the push tokens out. Fix them in the version you run now: give all but one monitor of each group a new push token, or remove the domain from all but one of its status pages. Then upgrade again. A status page that lists one domain twice in different cases keeps the oldest, a domain that is empty is removed, and a monitor that has its push token only in its config gets it as its push token. `bun db import-mongo` fills a push token from the config the same way.
  - Upgrade note: the TLS information and notification history of monitors that no longer exist are removed. They were not shown anywhere.
  - `bun db import-mongo` stores no push token as none, clears a push token that an earlier monitor holds, normalizes domains and gives a domain that two status pages held to the first, and its report counts each.
- feat: a new monitor's form ticks the notification channels marked as default, which you can untick. A clone keeps its source's channels and an edit keeps the monitor's own. The first channel made in Get started is one.
- feat: the public status pages and the badges of a suspended workspace answer 503 with the code `STATUS_PAGE_UNAVAILABLE` and the message "This status page is unavailable", and say nothing of why, whichever hold the workspace is under, including a new account's workspace while it waits for its owner's email verification. A page that is not published still answers 404. They answered as usual before.

### Added

### Changed

- chore: the Helm chart's bundled PostgreSQL and Redis (off by default) move to the Bitnami subcharts `postgresql` 18.12.16 and `redis` 28.3.10, with the latest PostgreSQL 18.6.0 and Redis 8.10.3 images

  - Upgrade note: switch `peekaping-bundle-sqlite` to `peekaping` in your compose file or `docker run` line. The old name gets no tags after 0.1.0. See [Upgrading to single mode](apps/docs/docs/self-hosting/upgrading-to-single-mode.md)
- fix: a failing monitor is checked again after its retry interval while it has retries left, and after its interval once they are used up. Before, the retry interval setting did nothing and every check waited the full interval. Max retries 0 or a retry interval of 0 keeps the interval (#582)
- fix: a new monitor's first failed check counts toward max retries like any other, so it is Pending while retries are left and Down after them. Before, the first failed check was Down at once and notified, even with retries left (#580)
- fix: a monitor's first heartbeat notifies only when it is Up or Down. A new monitor that starts Pending, or in a maintenance window, no longer sends a notification (#579)
- fix: the check timeout can be at most 0.8 × the check interval. The API answers 400 to a longer timeout on create, update and PATCH, and the monitor form shows an error under the timeout field. Before, the rule compared the wrong way round and PATCH didn't check it at all, so a timeout above the interval made the scheduler skip every second check (#584, #590)
  - Upgrade note: a monitor already stored with a longer timeout keeps being checked. Saving it again asks for a shorter timeout, or a longer interval.
- fix: notification channel URLs that hold credentials come back from the API masked, such as `https://user:********@host/x?token=********`. This covers the webhook URL, the ntfy, Gotify, WhatsApp and Telegram server URL, the Matrix homeserver URL, the PagerDuty integration URL and the Signal URL. Saving or testing a channel with the URL as shown keeps the stored one. To change a masked URL, type its credentials again: the form asks for them (#594, #595)

### Fixed

- fix: creating a push monitor through the API without a push token works. The server generates a token and returns it in `push_token` and in `config.pushToken`, where before it answered 400 (`PushConfig.PushToken ... required`). A token sent only as `push_token` is copied into `config.pushToken`, and a token you send is kept (#273, #574) (thanks @ausebiblibre)
- fix: a public status page shows a monitor that hasn't been checked yet, or is retrying, as Pending, not Down, and doesn't count it as an outage (#585)
- fix: the monitor page keeps getting live heartbeats. A room join sent right after the socket connected could be lost, and the page sent a leave and a join each time its data refetched, which could leave it out of the room (#592, #593)
- fix: TCP monitors work with a bracketed IPv6 host such as `[::1]` again (#118, #461) (thanks @miniwestxyz, @SynapShift)
- fix: PagerTree alerts for a monitor carry one stable `id`, so an Up resolves the alert its Down opened. The payload uses the lowercase keys PagerTree reads (#578)
- fix: each monitor's Grafana OnCall alerts go to an alert group of their own (`alert_uid` `Peekaping/<monitor id>`). Before, all monitors shared one group, and any monitor's Up resolved it while others were still Down (#576)
- fix: the ntfy topic is no longer logged, and email notifications are no longer printed to stdout with their recipient, subject and body (#577)
- fix: after a logout, the web app stops sending the previous user's access token. Before, it kept sending it until the page was reloaded (#583)
- fix: a wrong code when turning on two-factor authentication gets a 400 and an error, and two-factor stays off. Before, the API answered 200 and the web said two-factor was on when it wasn't (#586)

## [0.0.48] - 2026-10-27

### Added

- feat: `NOTIFICATION_HISTORY_RETENTION_DAYS` and `TLS_INFO_RETENTION_DAYS` set how many days the hourly cleanup keeps notification history (90 by default, at least 30, so the default certificate expiry notifications at 21 days aren't sent twice) and monitors' TLS information (30 by default, at least 1). They apply to the api and to `peekaping`, and a value below its minimum stops startup. Unset or `0`, nothing changes. See [Cleanup Configuration](apps/docs/docs/architecture/api-server.md#cleanup-configuration) (#75)
- feat: `bun db import-mongo --mongo-uri <uri> [--mongo-db <name>]` (or `MONGO_URI` and `MONGO_DB` in the environment, which keeps a password out of the shell history) moves a MongoDB install to SQLite or PostgreSQL. ### Fixed

- fix: the monitor list, batch, create and update responses now include `notification_ids` and `tag_ids`, like `GET /monitors/{id}`, which now also returns `push_token` (#191)
- fix: in cluster mode, the hourly cleanup (heartbeats past the data retention period, expired stats, old notification history, old TLS information) ran on every api replica at the same time. It now runs once an hour however many replicas run: the replicas claim the hour with a Redis key (`peekaping:cleanup:<hour>`, kept for two hours, where the hour is the time rounded to the nearest hour in UTC, so replicas whose clocks are less than an hour apart share one claim), and only the replica that wins logs `Running the hourly cleanup`. The others log at debug level that another replica has it. A replica that can't reach Redis when the hour starts logs an error and skips that hour, and the next hour tries again. In single mode, `peekaping` runs the cleanup every hour in its process, with no Redis. The four cleanups are one job now, so they run one after the other, and the cron fires at the top of the UTC hour, which only moves the time in time zones offset by part of an hour. A failure to schedule the cleanup used to be ignored; it now stops startup with an error (#75)
- fix: security: the API lets a page read its responses only from the origins in the new `CORS_ORIGINS` setting. Before, it answered every origin with `Access-Control-Allow-Origin: *`, so a page on any site could read them. `CORS_ORIGINS` is a comma-separated list of origins, such as `https://status.example.com,http://localhost:8383`. Unset, it is the origin of `CLIENT_URL`, and `*` alone allows any origin. A request from another origin is still served; its browser just won't hand the response to the page. Responses no longer carry `Access-Control-Allow-Credentials`, which the API never needed because its token travels in the `Authorization` header. An entry that isn't an origin stops startup, and `/metrics` stays unreadable from another origin. See [API Server](apps/docs/docs/architecture/api-server.md#security-configuration) (#55)
  - Upgrade note: a setup where a page on an origin other than `CLIENT_URL`'s calls the API must set `CORS_ORIGINS` to that origin, or the browser refuses it. The web app the bundles, the cluster gateway and the Helm chart serve calls the API on its own origin and needs nothing. The dev Compose files set `CORS_ORIGINS` to `http://localhost:8383` for the web container.
- fix: security: the login lockout no longer trusts a client's `X-Forwarded-For`. It counted failed logins under the leftmost address in that header, so a client could send a different one with every request and never be locked out, in every deployment. The API now believes `X-Forwarded-For` and `X-Real-IP` only from the proxies in the new `TRUSTED_PROXIES` setting (comma-separated IP addresses and CIDR ranges; its own default is empty, which believes no header, as in the single-mode bundles, while the cluster compose files and the Helm chart set loopback and the private ranges when it is unset, and an explicitly empty value there trusts nobody). For a request from one of them, the client is the last `X-Forwarded-For` address that isn't a trusted proxy (the leftmost when all are), or the `X-Real-IP` when there is no `X-Forwarded-For`; an `X-Forwarded-For` it can't read makes the client the proxy's own address. A request from any other address counts as coming from the address it connected from. A second counter now locks an account whatever addresses the guesses come from: `BRUTEFORCE_ACCOUNT_MAX_ATTEMPTS` failed logins (100 by default) within `BRUTEFORCE_ACCOUNT_WINDOW` (10 minutes) lock the account for `BRUTEFORCE_ACCOUNT_LOCKOUT` (1 minute). The count of failures is kept until the window, measured from the first failure, has passed, so until then each further failure after a lock ends locks the account again: guessing is bounded to the limit per window plus one attempt each time a lock ends, and after an attack stops the owner is back in within the window at most. An attacker who keeps going can keep the account locked. A successful login resets both counters. A login request body over 64 KiB is refused with 413. The cluster compose files and the Helm chart set `TRUSTED_PROXIES` for their gateway, and the cluster `nginx.conf` now replaces the client's `X-Forwarded-For` with its address. See [Reverse proxy and HTTPS](apps/docs/docs/self-hosting/docker-with-sqlite.md#reverse-proxy-and-https) (#50)
  - Upgrade note: if you run Peekaping behind your own proxy, make the proxy put the client's address last in `X-Forwarded-For` (Caddy and Traefik do; plain nginx `proxy_pass` forwards the client's own header, so add `proxy_set_header X-Forwarded-For $remote_addr;`) and set `TRUSTED_PROXIES` to the address the proxy connects from. For a proxy on the same Docker host, publish port 8383 on loopback (`-p 127.0.0.1:8383:8383`) and use the gateway of Docker's network, such as `TRUSTED_PROXIES=172.17.0.1`; don't trust that address while 8383 is published on all interfaces, because direct connections can arrive from it too. Until you do, the API sees every login as coming from the proxy, so one person's failed logins can lock an account for everyone. Installs with no proxy in front, and the cluster compose files and the Helm chart as shipped, need no change. A cluster install with its own `nginx.conf` needs `proxy_set_header X-Forwarded-For $remote_addr;` in the `/api/` and `/socket.io/` locations, as the new `nginx.conf` has. An Ingress that passes the client's `X-Forwarded-For` through unchanged needs `config.env.TRUSTED_PROXIES: ""` in the Helm values. A malformed `TRUSTED_PROXIES` stops the API at start.
- fix: security: login tokens and API keys are verified more strictly (#54).
  - Login tokens are accepted only when signed with HS256. The signing secrets stay in memory and are read from the database again after a minute, instead of on every request, so a secret changed in the database is used within a minute.
  - API keys are checked with SHA-256 and a constant-time compare, which cost far less than bcrypt on every request. A key created before this change keeps working, and its stored hash is replaced on its first use.
  - A key with a usage limit is never accepted more often than its limit, also when requests arrive together: checking the limit and counting the use are one database update.
  - A refresh token issued before a password change no longer works, so the sessions signed in with the old password can't renew. An access token already issued stays valid until it expires, within 15 minutes by default.
  - Registrations that arrive together on a new install create one admin. The others fail with "admin already exists".
  - The websocket reads the access token from the socket.io `auth` payload. A token in the query string is no longer accepted, so it stops showing up in a proxy's access logs. The web app sends it that way.
  - Upgrade note: every user signs in again once, because refresh tokens issued by earlier releases are rejected.
  - Upgrade note: after its first use, an API key is stored as a SHA-256 hash, which earlier releases can't check. After a rollback, recreate the keys used since the upgrade.
  - Upgrade note: a script or tool that opens the websocket itself must pass the token as `auth: { token }` instead of `query: { token }`.
- fix: creating a monitor, notification channel or maintenance window with `active: false` now stores and returns it as inactive. Bun replaced the false value with the column's `true` default on insert, so creates always came back active; editing afterwards worked. Omitting `active` when creating still produces an active resource (#394)
- fix: the Helm chart's web pods copy the web app from the web image you set. - fix: when the web app talks to the API on another URL (`API_URL`), a page load sends each API request once, to the API. Before, the first requests (the version check and the custom-domain lookup) went to the web app itself, failed, and ran again against the API (PP-210)
- fix: a data retention period of 0, a negative number or a very large number no longer makes the hourly cleanup delete every heartbeat. The settings API returns 400 unless `KEEP_DATA_PERIOD_DAYS` is a whole number of days from 1 to 36,500 with type `int`. If an invalid value was stored before, or the setting can't be read, the cleanup logs an error and deletes no heartbeats instead of falling back to 365 days (#337)
- fix: the hourly cleanup deletes expired heartbeats 5,000 at a time on SQL databases instead of in one statement, so a large backlog, such as the first run after lowering the data retention period, no longer blocks the API. On SQLite, deleting a million heartbeats used to hold the database for about 13 seconds; now no request waits more than about half a second. A migration replaces three heartbeat indexes that no query uses with one on the heartbeat time, which the cleanup deletes through. Each heartbeat gets about 15% smaller on SQLite, and loading a monitor's event history gets faster. The migration builds the new index, about 1 second per million heartbeats; on PostgreSQL new heartbeats wait while it does. On SQLite the database file stops growing but doesn't shrink on its own (#336)
- fix: a network reconnect (a laptop waking, say) no longer wipes a half-filled form. The app re-checks the custom-domain lookup in the background and keeps the current screen mounted, instead of unmounting every route for the length of the refetch (#161, #228, PP-196)
- fix: minute and hour stats have bounded retention. Every hour, minute stats older than 48 hours and hour stats older than 90 days are deleted; day stats are kept indefinitely and add about 365 rows per monitor each year. Uptime % and badges read minute stats for up to 24 hours and hour stats for up to 90 days, and charts read less. On SQL databases the rows are deleted 5,000 at a time, so the first run after upgrading clears a year of backlog without blocking the API. SQLite reuses freed pages, but its file does not shrink automatically (#315)
- docs: explain SQL stats upgrade history limits, backups and rollback, and provide a manual SQLite disk-space reclamation procedure. The migration drops the mixed legacy stats table and rebuilds history only from retained heartbeats; take a database backup before upgrading. See [Upgrading stats storage](apps/docs/docs/self-hosting/upgrading-stats.md) (PP-101)
- fix: heartbeats for the same monitor that the ingester handles at the same time no longer overwrite each other's counts in the stats behind the response time chart and uptime %, and no longer fail with a unique-key error. On MongoDB they no longer create a second stats document for the same minute, hour or day. Each heartbeat now updates its stats with 3 statements instead of 6 to 9 (#312)
- fix: the ingester logs an error with the monitor ID when it can't aggregate a heartbeat into the stats behind the response time chart and uptime %, instead of dropping the error (#260)
- fix: the API, producer, worker and ingester binaries embed the time zone database, so `TZ=Europe/Kyiv` and maintenance windows with their own time zone work in any image instead of falling back to UTC, and a time zone that fails to load logs a warning. "Same as Server Timezone" is the zone the process runs in. Upgrade note: the separate API, producer, worker and ingester images (Docker Compose, Helm) used to ignore `TZ` and run in UTC; after upgrading they run in the `TZ` you set (the example `.env` files set `America/New_York`), so "Same as Server Timezone" windows, log timestamps and times in notification messages move to that zone. Set `TZ=UTC` to keep the old behavior. The bundle images already honored `TZ` (#261, #262) (thanks @brewle)
- fix: the monitor page header shows the target of TCP, DNS, ping, Docker, gRPC, SNMP, MQTT, Kafka and RabbitMQ monitors, such as `1.1.1.1:443` or `example.com (A @ 8.8.8.8:53)`, instead of only the monitor type. Monitors whose target holds credentials or a token (database, Redis and push monitors) still show only the type. Only `http(s)` URLs are links (#269, #270, #308) (thanks @HartD92)
- fix: a status page that isn't published returns 404 on its public slug, custom domain and monitor routes, instead of serving its title and monitors. The View button on a draft status page therefore shows a 404 until the page is published (#305)
- fix: badges are served only for monitors on a published status page. A monitor that is only on a draft page gets no badge, and a failed status page lookup returns 500 instead of serving the badge (#305)
- fix: updating, pausing, resuming or deleting a monitor, maintenance window, notification channel, proxy, tag, status page or API key that doesn't exist returns 404 instead of reporting success, and so do the heartbeat, stats and TLS routes of a monitor that doesn't exist (#305)
- fix: the certificate expiry badge and the monitor TLS endpoint no longer fail with 500 on SQL databases for a monitor without certificate info, and the response time badge shows "N/A" instead of "N/Ams" before the first heartbeat (#305)
- fix: invalid updates return 400: a proxy's port or protocol in a partial update, a monitor's config in a partial update (checked against its type), and a maintenance window's partial update. A maintenance window's start and end time must be a valid HH:MM time; they weren't checked before (#305)
- fix: the settings API serves only `KEEP_DATA_PERIOD_DAYS` and returns 404 for every other key, so callers can no longer read, change or delete the JWT signing secrets. Upgrading generates new signing secrets, which signs everyone out once. With more than one API replica, old and new pods reject each other's tokens until the rolling update finishes, so users can be signed out again during it; to avoid that, run `kubectl scale deployment <release>-api --replicas=0` before `helm upgrade`, which scales it back up (#302)

- fix: editing, pausing or deleting a monitor drops its queued check and cancels a running one, so no result of the old config is recorded and the next check uses the current config, right away after an edit (#266)
- fix: close idle HTTP connections after each check, so HTTP monitors no longer leak one socket per check (#287) (thanks @jonfriesen)
- fix: ping monitors report an unreachable host as DOWN instead of "ping: executable file not found", no longer pick up other monitors' replies, work without root where unprivileged ICMP is allowed, and support IPv6 targets (#226, #297)
- fix: editing a monitor, or creating one, no longer overwrites its stored status. The monitor list's status filter and the status badge read that stored status, so an edited Down monitor was listed under Up and its badge said Up. A new monitor starts as Pending, and on start the API repairs monitors whose stored status differs from their latest heartbeat's (#285, #352, #353)
- fix: a push monitor's heartbeat is recorded as Maintenance, with the maintenance message, while the monitor is in a maintenance window, instead of the status the push reported. If the maintenance check fails, the push's own status is used (#349) (thanks @dajiaohuang)
- fix: a push URL with `status=down` is recorded as Down, and its `ping` as the response time. Before, `down` failed to parse and counted as Up, and `ping` was ignored (#298) (thanks @sean0407)
- fix: a gRPC monitor whose target can't be reached is Down. Before, any failure produced a made-up `SERVING` response, so it showed Up; the default method `check` also didn't match the proto's `Check`. A DNS monitor stops at its timeout instead of waiting 10 to 20 seconds on a resolver that never answers (#303)
- fix: on SQLite, a cancelled request no longer makes every API write fail with `database is locked (517)` until the API restarts. The SQLite driver is upgraded to a version that closes the cancelled query's rows (#346)
- fix: the monitor list card showed Pending and Maintenance monitors as Up, and the monitor page showed Pending as Down. Both show Up, Down, Pending or Maintenance by name (#344)
- fix: after the socket reconnects, the monitor list keeps updating live instead of freezing until the page is reloaded (#343)
- fix: a certificate expiry notice goes out once per threshold, such as 21, 14 and 7 days, instead of stopping after the first. A certificate first seen inside several thresholds gets only the nearest one, not all at once (#324)
- fix: a recurring-interval maintenance window counts calendar days in its time zone. Before, it was active on the wrong days around midnight and daylight saving changes, so alerts fired during planned maintenance and were muted outside it. A single date-range window now includes its first minute (#323)
- fix: failed logins lock an account on SQLite and MongoDB, as they do on PostgreSQL. The lock never applied there before. After `BRUTEFORCE_MAX_ATTEMPTS` failures (20 by default) within `BRUTEFORCE_WINDOW` (1 minute by default), the account is locked for `BRUTEFORCE_LOCKOUT` (1 minute by default). On every database, `BRUTEFORCE_MAX_ATTEMPTS=1` now locks after one failure instead of two (#313)
- fix: setting up 2FA a second time before verifying the first showed a QR code whose codes never verified, and a failed save of the 2FA status still answered "2FA verification successful" (#314)
- fix: the production Docker Compose files and the self-hosting guides give `web` and `gateway` `restart: unless-stopped`, so the nginx gateway no longer stays stopped after a Docker restart. Add the two lines to a compose file you copied earlier (#33, #331)
- fix: the Telegram channel's template hint names `{{ monitor.name }}` instead of a variable that doesn't exist (#253, #281) (thanks @dimonl)
- fix: uptime % on the monitor page (24h, 7d, 30d and 365d) and the 24h, 30d and 90d badges count the right window. They read day stats, which count only when the day starts inside the window, so "24h" meant since midnight UTC and 7d and 30d dropped everything before the first midnight (#320)
- fix: SQL databases keep minute, hour and day stats in their own tables (`stat_minutely`, `stat_hourly`, `stat_daily`). Before, one table mixed the three scales, so the 14:00 minute row also held the whole 14:00 hour, and maintenance checks lowered the average response time. Upgrade note: a migration creates the tables, rebuilds them from the heartbeats you still have and drops the old `stats` table; take a backup first, as the docs entry above says (#306)
